۱. معماری و نگاشت به منابع Kubernetes

هدف بخش اول، تثبیت معماری منطقی سیستم بانکداری توزیع‌شده و تعیین نگاشت دقیق هر جزء به منبع مناسب Kubernetes است تا استقرار بعدی روی یک طرح واحد انجام شود و routing با تعویض Podها نشکند.

۱.۱ قواعد دامنه و مرزهای صحت

قواعد دامنه و مرزهای صحت بدون تغییر باقی می‌مانند:

  • شاردینگ حساب‌ها: بازهٔ A برابر ۱–۱۰۰۰ و بازهٔ B برابر ۱۰۰۱–۲۰۰۰
  • چند replica برنامه‌ای روی هر shard، با یک پایگاه‌دادهٔ مشترک همان shard
  • Gateway آگاه از shard و انتخاب replica سالم برای سرویس‌دهی
  • Coordinator با پروتکل 2PC و ثبت ماندگار تصمیم تراکنش
  • قیود صحت: بدون موجودی تکراری، بدون transfer ناقص دائمی، و بدون اعلام موفقیت برای نتیجهٔ نامعلوم

تفاوت اصلی در لایهٔ اجراست. به‌جای کانتینرهای ثابت Compose، workloadها به‌صورت Pod روی خوشه اجرا می‌شوند و باید در برابر حذف Pod، تغییر مقیاس، rolling update و شکست پایگاه‌داده همچنان در دسترس و صحیح بمانند.

۱.۲ معماری منطقی

کلاینت فقط با Gateway صحبت می‌کند؛ Gateway درخواست‌های محلی را به shard مربوط و درخواست‌های cross-shard را به Coordinator می‌فرستد. هر لایهٔ اپ به پایگاه‌دادهٔ خودش وابسته است. روی Kubernetes، هویت پایدار برای ارتباط داخلی از نام Service گرفته می‌شود، نه از IP موقتی Pod.

۱.۳ نگاشت اجزا به منابع Kubernetes

انتخاب نوع منبع بر اساس نقش هر جزء در سیستم انجام شده است. سرویس‌های بدون state محلی (Gateway، bank، coordinator، console) با Deployment مدیریت می‌شوند تا بتوان آن‌ها را scale کرد و پس از حذف Pod دوباره ساخت. پایگاه‌های داده که به هویت پایدار و دیسک نیاز دارند با StatefulSet و PersistentVolumeClaim مستقر می‌شوند. کشف و مسیریابی داخلی از طریق Service انجام می‌گیرد و دسترسی خارجی در فاز اول با NodePort فراهم می‌شود.

جزء در Compose منبع Kubernetes توجیه
gateway Deployment + Service (ClusterIP) + NodePort نقطهٔ ورود کلاینت؛ بدون state محلی؛ باید پس از تعویض Pod همچنان از بیرون در دسترس باشد
bank-a* / bank-b* Deployment per shard + Service per shard چند replica برنامه‌ای روی هر shard؛ توزیع ترافیک روی endpointهای Ready
coordinator Deployment + Service منطق 2PC بدون state محلی در فرآیند؛ ماندگاری تصمیم‌ها در db-coord
console Deployment + Service (دسترسی خارجی اختیاری) رابط آزمایشگاهی برای مشاهده و اجرای سناریوها
db-a / db-b / db-coord StatefulSet + PVC (و در ادامه primary/standby) داده باید پس از حذف یا جابه‌جایی Pod باقی بماند؛ هویت پایدار برای replication لازم است
config/shard_map.json ConfigMap پیکربندی غیرحساس و قابل نسخه‌گذاری جدا از ایمیج
رمز عبور و credentialهای پایگاه‌داده Secret جداسازی اسرار از ایمیج و Manifestهای عمومی

۱.۴ استقرار فیزیکی هدف روی Minikube

استقرار هدف در یک namespace جدا (مثلاً banking) روی Minikube تعریف می‌شود. شکل ۲ رابطهٔ Deploymentها، Serviceها و StatefulSetها را نشان می‌دهد. Gateway به نام Service بانک‌ها و Coordinator وصل می‌شود؛ بانک‌ها به Service مربوط به پایگاه‌دادهٔ همان shard؛ و ماندگاری داده روی PVC پشت StatefulSetها قرار می‌گیرد. replication واقعی primary/standby در بخش مربوط به failover اضافه می‌شود.

۱.۵ جریان درخواست و پایداری routing

در Kubernetes عمر Pod محدود است و با هر recreate، آدرس IP عوض می‌شود. اتصال مستقیم Gateway به IP یک Pod پس از restart همان Pod مسیر را می‌شکند. طراحی این سیستم Gateway را فقط به نام Service متصل می‌کند؛ برای مثال http://bank-a:8000. کنترل‌پلن Kubernetes فهرست endpointهای Ready را به‌روز نگه می‌دارد و ترافیک فقط به Podهای سالم هدایت می‌شود. همین سازوکار پایهٔ تحمل خطای سطح اپ و آماده‌سازی برای readiness probe است.

۱.۶ تصمیم‌های طراحی تثبیت‌شده

  • خوشهٔ هدف: Minikube روی میزبان توسعه
  • جداسازی منطقی با namespace اختصاصی (مثلاً banking)
  • دسترسی خارجی فاز اول از طریق NodePort
  • workloadهای اپلیکیشن با Deployment؛ پایگاه‌های داده با StatefulSet و PVC
  • ارتباط داخلی صرفاً از طریق DNS سرویس Kubernetes
  • بازیابی سطح اپلیکیشن با کنترلرهای بومی Kubernetes (Deployment، probes، Endpoints)

۲. استقرار هسته روی Minikube

هستهٔ سیستم در namespace banking با Manifestهای پوشهٔ 3/k8s/base مستقر می‌شود. منطق دامنه بدون تغییر است؛ بستر اجرا از Docker Compose به Kubernetes منتقل شده است. برای جلوگیری از تداخل پورت و ابهام مسیر ترافیک، استک Compose خاموش می‌شود و فقط خوشهٔ Minikube سرویس‌دهی می‌کند.

۲.۱ خاموش‌کردن استک Compose

کانتینرهای Compose و Podهای Kubernetes هم‌زمان لازم نیستند. با پایین آوردن پروژهٔ Compose، پورت‌های میزبان آزاد می‌شوند و مشخص است که ترافیک از مسیر Kubernetes می‌آید. ایمیج‌ها روی دیسک می‌مانند؛ فقط کانتینرهای در حال اجرا متوقف می‌شوند.

۲.۲ استفاده از ایمیج‌های محلی (بدون دانلود مجدد)

Manifestها به همان ایمیج‌هایی اشاره می‌کنند که قبلاً با docker compose build ساخته شده‌اند. مقدار imagePullPolicy: Never مانع pull از رجیستری می‌شود؛ بنابراین از GitHub/GHCR دوباره دانلود نمی‌شود.

۲.۵ نگاشت DNS و shard map

در Kubernetes، Gateway دیگر به نام‌های ثابت Compose مثل bank-a1 وابسته نیست. shard map به Serviceهای پایدار اشاره می‌کند: http://bank-a:8000 و http://bank-b:8000. خود Service ترافیک را بین Podهای Ready همان Deployment پخش می‌کند. Coordinator نیز از http://coordinator:8090 در دسترس Gateway است و پایگاه‌ها با نام‌های db-a، db-b و db-coord resolve می‌شوند. این تغییر عمدی است: با تعویض Pod، مسیر از روی نام Service درست می‌ماند.

محتوای shard map روی خوشه:

{
  "epoch": 1,
  "shards": {
    "A": { "start": 1, "end": 1000, "replicas": ["http://bank-a:8000"] },
    "B": { "start": 1001, "end": 2000, "replicas": ["http://bank-b:8000"] }
  }
}

۳. Persistence با PersistentVolumeClaim

لایهٔ اپلیکیشن بانک هیچ state محلی‌ای نگه نمی‌دارد و برای آن Deployment کافی است، چون موجودی حساب‌ها فقط در Postgres معنا دارد. مشکل اینجاست که خود Postgres اگر داده را داخل لایهٔ موقتی کانتینر یا emptyDir بنویسد، با هر بار حذف Pod آن داده هم از بین می‌رود. در آن صورت deposit یا transfer که از نظر کلاینت موفق بوده، بعد از recreate دیگر در دیسک نیست و صحت سیستم بانکی از بین می‌رود. بنابراین پایگاه‌های داده باید روی storageای بنشینند که عمرش از عمر Pod جدا باشد.

۳.۱ پیاده‌سازی و منطق طراحی

برای رسیدن به این هدف، در فایل‌های db-a.yaml، db-b.yaml و db-coord.yaml هر پایگاه به‌صورت StatefulSet تعریف شده و به‌جای volume ساده از volumeClaimTemplates استفاده می‌کند. وقتی StatefulSet بالا می‌آید، Kubernetes برای هر ordinal یک PersistentVolumeClaim جدا می‌سازد؛ مثلاً برای db-a-0 claim با نام پایدار data-db-a-0 ساخته می‌شود و همان volume به مسیر /var/lib/postgresql/data داخل کانتینر mount می‌گردد. متغیر PGDATA روی زیردایرکتوری pgdata تنظیم شده تا entrypoint رسمی ایمیج Postgres بتواند روی volume تازه‌مونت‌شده بدون خطای permission یا دایرکتوری خالی، catalog را مقداردهی اولیه کند.

اسکیمای جدول حساب‌ها و seed اولیه از ConfigMapهای db-init-* به پوشهٔ /docker-entrypoint-initdb.d mount می‌شود. این اسکریپت‌ها فقط وقتی اجرا می‌شوند که catalog هنوز ساخته نشده باشد؛ یعنی روی PVCای که از قبل داده دارد، دوباره موجودی‌ها را به هزار بازنشانی نمی‌کنند. انتخاب StatefulSet به‌جای Deployment برای پایگاه‌داده دقیقاً به همین دلیل است: نام پایدار Pod، PVC چسبیده به همان ordinal، و رفتار قابل پیش‌بینی هنگام حذف و ساخت مجدد. برای خوشهٔ تک‌نود Minikube، ReadWriteOnce و StorageClass پیش‌فرض کافی است. خود Deploymentهای bank هیچ PVCای ندارند، چون state آن‌ها در دیتابیس است و باید بتوانند آزادانه scale یا rolling شوند بدون اینکه موجودی را روی دیسک محلی Pod نگه دارند. 

volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      resources:
        requests:
          storage: 1Gi
# mountPath: /var/lib/postgresql/data
# PGDATA=/var/lib/postgresql/data/pgdata

۳.۲ نحوهٔ تست ماندگاری

ابتدا باید مطمئن شد PVCها واقعاً ساخته و به Volume وصل شده‌اند. نام claim از الگوی <claimName>-<podName> می‌آید و بعد از recreate همان claim باید Bound بماند. 

kubectl -n banking get sts,pvc -o wide
kubectl -n banking describe pvc data-db-a-0

آزمایش اصلی این است که موجودی را از مسیر Gateway عوض کنیم، Pod دیتابیس را عمداً حذف کنیم، و بعد از Ready شدن مجدد همان موجودی را دوباره بخوانیم. اگر لایهٔ persistence درست پیاده شده باشد، مقدار بعد از recreate باید دقیقاً همان مقدار بعد از deposit باشد؛ فقط IP Pod عوض می‌شود، نه داده روی دیسک.

تونل Gateway (ترمینال جدا) و سپس deposit و حذف Pod:

kubectl -n banking port-forward svc/gateway 8080:8080
Invoke-RestMethod http://127.0.0.1:8080/transaction -Method POST -ContentType "application/json" -Body '{"action":"balance","account":"A0500"}'
Invoke-RestMethod http://127.0.0.1:8080/transaction -Method POST -ContentType "application/json" -Body '{"action":"deposit","account":"A0500","amount":50}'
kubectl -n banking delete pod db-a-0
kubectl -n banking rollout status statefulset/db-a --timeout=120s
kubectl -n banking get pod db-a-0 -o wide
kubectl -n banking get pvc data-db-a-0
Invoke-RestMethod http://127.0.0.1:8080/transaction -Method POST -ContentType "application/json" -Body '{"action":"balance","account":"A0500"}'

۴. Primary / Standby و Failover

PersistentVolumeClaim فقط عمر داده را از عمر یک Pod جدا می‌کند. اگر خود primary از کار بیفتد یا همان volume موقتاً در دسترس نباشد، سیستم همچنان به یک کپی زنده‌ای نیاز دارد که commitهای قبلی را داشته باشد و بتواند جای writer را بگیرد. به همین خاطر برای هر shard بانک یک primary و یک standby با streaming replication واقعی Postgres پیاده شده است. db-coord در محدودهٔ هسته تک‌نسخه مانده، چون نقش آن ثبت تصمیم‌های 2PC است و الگوی HA آن جدا از مسیر موجودی حساب‌ها طراحی شده است.

۴.۱ پیاده‌سازی و منطق طراحی

برای هر shard دو StatefulSet جدا تعریف شده است؛ مثلاً db-a به‌عنوان primary اولیه و db-a-standby به‌عنوان replica فیزیکی، و همین الگو برای shard B تکرار می‌شود. جدا نگه‌داشتن این دو STS عمدی است: نقش‌ها، entrypoint، و حتی منطق bootstrap آن‌ها یکی نیست و نمی‌توان با replicas: 2 روی یک StatefulSet واحد، یکی را writer و دیگری را hot standby کرد. primary با آرگومان‌هایی مثل wal_level=replica، max_wal_senders و max_prepared_transactions بالا می‌آید تا هم بتواند WAL را برای standby بفرستد و هم تراکنش‌های prepared مربوط به 2PC را نگه دارد.

standby به‌جای entrypoint پیش‌فرض ایمیج Postgres، اسکریپت standby-entrypoint.sh را از ConfigMap db-ha-scripts اجرا می‌کند. این اسکریپت صبر می‌کند تا primary آماده شود، روی PVC خالی pg_basebackup -R می‌گیرد تا یک کپی فیزیکی همراه با تنظیمات replication بسازد، و بعد Postgres را در حالت hot_standby اجرا می‌کند. نقش replicator و قوانین pg_hba با اسکریپت enable-replication.ps1 فقط روی writer فعلی اعمال می‌شوند، چون standby در حالت recovery اجازهٔ ساخت نقش را ندارد.

نکتهٔ مهم برای لایهٔ اپ این است که bankها به نام ثابت یک Pod وصل نمی‌شوند. مقدار DATABASE_URL_A و DATABASE_URL_B در Secret به Serviceهای db-a-primary و db-b-primary اشاره می‌کند؛ این Serviceها با selector روی role=primary و shard-db فقط Pod نویسندهٔ فعلی را در Endpoints می‌گذارند. به این ترتیب هنگام failover، به‌جای عوض کردن URL داخل اپ، کافی است label نویسنده جابه‌جا شود. headless Serviceهایی مثل db-a و db-a-standby-hl همچنان برای هویت StatefulSet و ارتباط replication باقی مانده‌اند.

خود failover با failover-db.ps1 انجام می‌شود: ابتدا StatefulSet مربوط به primary مقیاسش به صفر می‌رسد، سپس روی standby دستور pg_promote زده می‌شود تا از حالت recovery خارج شود، و در پایان label role=primary روی همان Pod قرار می‌گیرد تا Service نویسنده به آن اشاره کند. اپ بانک همان URL قبلی را می‌بیند و نیازی به rebuild یا تغییر Secret ندارد. این طراحی یک writer در هر لحظه را حفظ می‌کند تا دو منبع حقیقت برای موجودی‌ها به‌وجود نیاید، و به‌جای کپی دستی جدول‌ها از replication مبتنی بر WAL استفاده می‌کند تا commitهای اخیر با lag کم روی standby دیده شوند.

۴.۳ نحوهٔ تست — Failover primary

برای اثبات صحت failover، ابتدا روی primary می‌نویسیم و همان مقدار را روی standby می‌خوانیم تا همگرایی تأیید شود؛ بعد primary را از مدار خارج و standby را promote می‌کنیم. معیار قبول این است که موجودی بعد از failover از Gateway همان مقدار بعد از deposit باشد و Service نویسنده فقط به Pod promoted اشاره کند.

۵. Probes و Self-Healing

در Kubernetes صرف Running بودن یک کانتینر به‌معنای آماده بودن برای سرویس بانکی نیست. ممکن است فرایند زنده باشد ولی به پایگاه‌داده وصل نشود، یا یک replica بمیرد و ترافیک همچنان به آدرس مرده برود. بنابراین سیستم باید دو چیز را از هم جدا کند: اینکه اپ از نظر شبکه سالم و وابسته به DB آماده است، و اینکه اگر یک Pod از بین رفت کنترلر خودش جایگزین بسازد بدون اینکه کل shard قطع شود.

۵.۱ پیاده‌سازی و منطق طراحی

در Manifestهای bank-a و bank-b — و به همین ترتیب برای gateway و coordinator — دو نوع probe روی GET /health تعریف شده است. readiness با دورهٔ کوتاه‌تر مشخص می‌کند آیا Pod باید در Endpoints سرویس بماند یا نه؛ اگر این probe شکست بخورد، Pod از چرخهٔ ترافیک خارج می‌شود ولی لزوماً کشته نمی‌شود، و Gateway دیگر درخواست را به آن نمی‌فرستد. liveness با تأخیر اولیه و آستانهٔ کندتر همان مسیر را نگاه می‌کند تا اگر فرایند واقعاً گیر کرد، kubelet کانتینر را restart کند. خود /health در bank_server به Postgres وصل می‌شود؛ در نتیجه قطع شدن دیتابیس باعث شکست health و NotReady شدن اپ می‌شود، حتی اگر وضعیت Pod هنوز Running باشد. روی خود Postgres از pg_isready استفاده شده است.

هر shard اپ با replicas: 2 بالا می‌آید تا حذف یک Pod ظرفیت آن shard را به صفر نرساند. بازیابی در این لایه با خود Deployment انجام می‌شود و نیازی به healer سفارشی بیرون از خوشه نیست. هدف طراحی دقیقاً همین تمایز است: در دسترس بودن اپ از در دسترس بودن DB جدا شود، و همزمان با کنترلرهای بومی Kubernetes رفتار قابل پیش‌بینی داشته باشیم. 

readinessProbe:
  httpGet: { path: /health, port: http }
  periodSeconds: 5
  timeoutSeconds: 3
  failureThreshold: 3
livenessProbe:
  httpGet: { path: /health, port: http }
  initialDelaySeconds: 20
  periodSeconds: 10

۵.۲ نحوهٔ تست — حذف یک Pod اپ

در این آزمون فقط یکی از دو Pod بانک حذف می‌شود تا دیده شود replica دیگر سرویس می‌دهد و Deployment بلافاصله جایگزین می‌سازد. Endpoints باید به ترکیب IP جدید به‌روز شود.

حذف یک Pod و مشاهدهٔ جایگزینی:

kubectl -n banking get pods -l app=bank-a -o wide
kubectl -n banking get endpoints bank-a
$pod = (kubectl -n banking get pods -l app=bank-a -o jsonpath='{.items[0].metadata.name}')
kubectl -n banking delete pod $pod
kubectl -n banking get pods -l app=bank-a -o wide
kubectl -n banking get endpoints bank-a
kubectl -n banking rollout status deploy/bank-a --timeout=120s

نتیجهٔ مورد انتظار این است که در تمام مدت حداقل یک Pod Ready بماند، Pod حذف‌شده جایگزین شود، و فهرست Endpoints سرویس به آدرس‌های سالم جدید به‌روز گردد.

۵.۳ نحوهٔ تست — قطع DB و اثر readiness

آزمون دوم تعمداً دیتابیس shard B را قطع می‌کند تا نشان دهد اپ ممکن است Running بماند ولی Ready نشود و از Endpoints خارج گردد. بعد از برگرداندن DB باید Ready و endpoint برگردند. در پایان enable-replication.ps1 دوباره زده می‌شود تا نقش replicator روی primary تازه‌ساخته برقرار بماند. 

kubectl -n banking scale sts/db-b --replicas=0
Start-Sleep -Seconds 20
kubectl -n banking get pods -l app=bank-b
kubectl -n banking get endpoints bank-b
kubectl -n banking scale sts/db-b --replicas=1
kubectl -n banking rollout status sts/db-b --timeout=120s
Start-Sleep -Seconds 15
kubectl -n banking get pods -l app=bank-b
kubectl -n banking get endpoints bank-b
cd "d:\University\3\Distributed Systems\Assignments\3\k8s"
.\scripts\enable-replication.ps1

در عمل هنگام قطع DB، Podهای bank-b همچنان Running دیده می‌شوند ولی به Ready 0/1 می‌روند و فهرست Endpoints خالی می‌شود؛ یعنی Service دیگر ترافیک به آن‌ها نمی‌دهد. پس از برگرداندن دیتابیس، Ready و endpoint بازمی‌گردند و نقش replicator دوباره روی writer تنظیم می‌شود.

۶. ConfigMap، Secret و NetworkPolicy

استقرار روی Kubernetes فقط بالا آوردن Pod نیست؛ باید مشخص باشد پیکربندی از کجا می‌آید، اسرار چگونه تزریق می‌شوند، و هر جزء حق دارد با چه کسی حرف بزند. اگر shard map داخل ایمیج پخته شود، هر تغییر routing نیازمند rebuild است. اگر رمز پایگاه در Deployment به‌صورت متن ساده تکرار شود، مدیریت و چرخش آن سخت می‌شود. و اگر هر Pod بتواند به هر پورت دیگری در namespace وصل شود، مرز امنیتی بین Gateway و دیسک دیتابیس عملاً وجود ندارد.

۶.۱ پیاده‌سازی ConfigMap و Secret

همهٔ این منابع در base/config.yaml تعریف و از طریق Kustomize اعمال می‌شوند. ConfigMap/shard-map فایل JSON مسیر سرویس‌های bank-a و bank-b را نگه می‌دارد و به‌صورت volume روی /config/shard_map.json داخل Gateway و Coordinator mount می‌شود؛ خود کانتینر فقط مسیر فایل را از env می‌گیرد. ConfigMapهای db-init-* اسکیمای اولیه و seed حساب‌ها را برای اولین راه‌اندازی روی PVC خالی فراهم می‌کنند، و db-ha-scripts اسکریپت bootstrap standby را جدا از ایمیج رسمی Postgres نگه می‌دارد تا بتوان بدون ساخت ایمیج سفارشی، رفتار replication را نسخه کرد.

اسرار و رشته‌های اتصال در Secret/db-credentials قرار دارند و با secretKeyRef به env کانتینرها تزریق می‌شوند. مثلاً bank-a فقط DATABASE_URL_A را می‌گیرد که به db-a-primary اشاره دارد؛ bank-b و coordinator هم الگوی متناظر خود را دارند. نتیجه این است که تغییر host یا رمز بدون rebuild ایمیج، با ویرایش Secret و یک rollout انجام می‌شود، و محتوای غیرحساس (مثل shard map) از محتوای حساس (مثل password) جدا می‌ماند.

۶.۲ پیاده‌سازی NetworkPolicy و مشاهده‌پذیری

در base/networkpolicy.yaml ابتدا یک سیاست default-deny-ingress برای تمام Podهای namespace گذاشته شده است؛ یعنی به‌صورت پیش‌فرض هیچ ورودی‌ای مجاز نیست مگر اینکه سیاست دیگری آن را صریحاً باز کند. سپس برای هر نقش، مسیرهای لازم باز می‌شوند: Gateway فقط روی پورت ۸۰۸۰ ورودی می‌پذیرد و خروجی‌اش به bankها و coordinator (به‌علاوه DNS) محدود است؛ bankها فقط از Gateway و coordinator ورودی می‌گیرند و خروجی‌شان فقط به writer همان shard روی پورت ۵۴۳۲ است؛ coordinator از Gateway ورودی می‌گیرد و به bankها و db-coord وصل می‌شود؛ و پایگاه‌های داده فقط از bank همان shard و peerهای replication همان shard-db ورودی دارند. مهم‌ترین محدودیت نمایشی این است که Gateway عمداً در فهرست مجاز Postgres نیست، تا حتی در صورت نفوذ به لبه، مسیر مستقیم به دیسک داده بسته بماند.

CNI پیش‌فرض Minikube یعنی kindnet این اشیاء NetworkPolicy را می‌سازد ولی enforce نمی‌کند. برای اینکه محدودیت واقعاً روی نود اعمال شود، اسکریپت enable-calico.ps1 مانیفست Calico را نصب و kindnet را برمی‌دارد تا کنترل‌کنندهٔ سیاست بتواند ترافیک غیرمجاز را قطع کند. در کنار این، مشاهده‌پذیری از چند کانال ساده تأمین شده است: لاگ‌های kubectl logs برای gateway و bank و coordinator، endpointهای /health برای آمادگی مسیر، /transactions/{id} و /requests/{client_request_id} برای وضعیت تراکنش، و metrics-server برای CPU مورد نیاز HPA.

ابتدا وجود ConfigMap و Secret و محتوای shard map بررسی می‌شود؛ سپس با یک اتصال مستقیم از داخل Pod مشخص می‌شود Gateway به پورت ۵۴۳۲ دیتابیس راه ندارد، در حالی که bank همان shard راه دارد و مسیر عادی بانکی از Gateway همچنان سالم است.

۷. Autoscaling با HPA

تعداد Podهای بانک نباید با یک kubectl scale دستی و دائمی تنظیم شود. انتظار سیستم این است که وقتی بار واقعی بالا می‌رود خودش ظرفیت اضافه کند، و وقتی بار فروکش کرد دوباره جمع شود، بدون اینکه موجودی حساب‌ها به‌خاطر عوض شدن تعداد replica خراب شود. این فقط وقتی ممکن است که state بانکی بیرون از Pod باشد و کنترلر مقیاس بر اساس متریک منابع کار کند، نه حدس اپراتور.

۷.۱ پیاده‌سازی و منطق طراحی

روی هر container بانک در Manifest، هم resources.requests و هم limits تعریف شده است؛ بدون request، درصد CPU برای HPA معنای پایداری ندارد. فایل base/hpa.yaml دو شیء HorizontalPodAutoscaler می‌سازد که به Deployment/bank-a و bank-b وصل‌اند. حداقل replica برابر ۲ است تا با نیاز self-healing بخش قبل هم‌خوان بماند، و حداکثر ۵ تا سقف منابع Minikube رعایت شود. هدف utilization متوسط CPU روی ۵۰٪ گذاشته شده و رفتار scaleUp نسبت به scaleDown تهاجمی‌تر است تا بار ناگهانی زودتر جذب شود، ولی جمع‌شدن ظرفیت با تأخیر و محافظه‌کاری بیشتری انجام شود و نوسان کوتاه سیستم را بالا و پایین نکند.

منبع متریک، addon metrics-server است که در apply.ps1 فعال می‌شود. برای تولید بار، اسکریپت load-gateway.ps1 چند worker موازی را روی /transaction می‌فرستد. چون موجودی‌ها در Postgres هستند نه در حافظهٔ Pod، زیاد و کم شدن تعداد replica اپ نباید به‌خودی‌خود موجودی را تغییر دهد؛ همین ویژگی است که اجازه می‌دهد مقیاس‌پذیری و صحت بانکی هم‌زمان معنا داشته باشند.

۸. Rolling Update و Rollback

تغییر نسخهٔ اپ یا تنظیمات آن نباید همهٔ replicaهای یک shard را هم‌زمان خاموش کند. همچنین اگر rollout معیوب از آب درآمد، باید بتوان بدون دستکاری دستی موجودی‌ها به revision قبلی برگشت. چون state بانکی داخل Pod نیست و در Postgres می‌ماند، خود مکانیزم Deployment می‌تواند Podها را یکی‌یکی عوض کند، به شرطی که استراتژی rollout ظرفیت Ready را حفظ کند.

۸.۱ پیاده‌سازی و منطق طراحی

در Deploymentهای bank-a و bank-b استراتژی RollingUpdate با maxUnavailable: 0 و maxSurge: 1 صریحاً نوشته شده است. معنای عملی این تنظیم آن است که هنگام آپدیت، ابتدا یک Pod جدید ساخته و Ready می‌شود و بعد یکی از Podهای قدیمی حذف می‌گردد؛ در نتیجه ظرفیت Ready به زیر حداقل تعیین‌شده نمی‌افتد، و همزمان فقط یک واحد اضافی روی منابع Minikube فشار می‌آورد. کلاینت همچنان فقط Service مشترک را می‌بیند و کاری به نام موقتی Podها ندارد. 

strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 0
    maxSurge: 1

برای دموی کنترل‌شده، به‌جای rebuild کامل ایمیج، با kubectl set env deploy/bank-a DEMO_ROLLING=v2 یک تغییر بی‌ضرر در pod template ایجاد می‌شود تا ReplicaSet جدید ساخته شود. اگر این rollout نامطلوب باشد، kubectl rollout undo همان Deployment را به revision قبلی برمی‌گرداند. rollout status پیشرفت را نشان می‌دهد و rollout history تاریخچهٔ revisionها را نگه می‌دارد. این مسیر عمداً از قابلیت بومی کنترلر استفاده می‌کند تا نیاز به اسکریپت بازگردانی دستی Pod نباشد.

۸.۲ نحوهٔ تست زیر بار

همزمان با تولید بار روی یک حساب، rollout و سپس rollback اجرا می‌شود. معیار قبول این نیست که هیچ خطای موقت اتصالی دیده نشود — در پنجرهٔ تعویض Pod چنین خطاهایی طبیعی‌اند — بلکه این است که بعد از اتمام عملیات، موجودی در دیتابیس فاسد یا دوبار اعمال نشده باشد. 

.\scripts\load-gateway.ps1 -Seconds 55 -Workers 6 -Account A0900 -Action balance
kubectl -n banking set env deploy/bank-a DEMO_ROLLING=v2
kubectl -n banking rollout status deploy/bank-a --timeout=180s
kubectl -n banking rollout undo deploy/bank-a
kubectl -n banking rollout status deploy/bank-a --timeout=180s
kubectl -n banking rollout history deploy/bank-a
Invoke-RestMethod http://127.0.0.1:8080/transaction -Method POST -ContentType "application/json" -Body '{"action":"balance","account":"A0900"}'

در اجرای ثبت‌شده، هم rollout و هم rollback کامل شدند و موجودی A0900 برابر 1000.0 ماند. بخشی از درخواست‌های همزمان در همان پنجره خطای موقت گرفتند، اما فساد داده یا اثر تکراری روی موجودی دیده نشد.

۹. آزمایش‌های اجباری و شواهد صحت

هفت آزمایش اجباری برای این طراحی شده‌اند که هر کدام یکی از مکانیزم‌های بخش‌های قبل را زیر فشار یا شکست واقعی بگذارند. معیار قبول فقط پاسخ HTTP نیست؛ موجودی در Postgres و برای انتقال‌های بین‌shard وضعیت ردیف‌های distributed_transactions در پایگاه coord هم باید با نتیجهٔ اعلام‌شده هم‌خوان باشد. اجرای خودکار این سناریوها در scripts/run-core-experiments.ps1 و run-experiments-3to7.ps1 آمده و لاگ خام در report/experiment-results/ ذخیره شده است.

۹.۱ روش اندازه‌گیری

تمام ترافیک کلاینت فقط از Gateway و از طریق port-forward به پورت ۸۰۸۰ وارد می‌شود تا مسیر واقعی سرویس‌دهی همان مسیری باشد که کاربر خارجی می‌بیند. موجودی مرجع با psql روی Podی خوانده می‌شود که label role=primary دارد، نه لزوماً روی نام تاریخی db-*-0. برای تراکنش‌های توزیع‌شده، وضعیت تصمیم و شرکت‌کنندگان از دیتابیس coordinator خوانده می‌شود. اگر HTTP موفقیت بگوید ولی DB چیز دیگری نشان دهد، آزمایش مردود است.

۹.۲ خلاصهٔ نتایج و معنای هر آزمایش

آزمایش ۱ با حذف یک Pod از bank-a نشان می‌دهد Deployment دو‌نسخه‌ای و به‌روزرسانی Endpoints کافی است تا shard هنگام heal همچنان سرویس بدهد؛ deposit روی A0600 در همان پنجره در DB به 1010.00 رسید. آزمایش ۲ با failover واقعی روی shard B ثابت می‌کند streaming standby و Service نویسنده می‌توانند بعد از از دست رفتن primary، موجودی commit‌شده را نگه دارند؛ A1500 قبل و بعد 1016.0 ماند. آزمایش ۳ بیست deposit موازی روی یک حساب را اجرا می‌کند تا ایزولاسیون نوشتن از چند replica اپ روی یک Postgres مشترک بررسی شود؛ موجودی نهایی دقیقاً برابر شروع به‌علاوه تعداد موفقیت‌ها شد.

آزمایش ۴ Pod مربوط به coordinator را وسط یک transfer بین‌shard حذف می‌کند. هدف این است که تصمیم 2PC روی db-coord ماندگار بماند و پس از بالا آمدن مجدد، وضعیت درخواست از /requests/{id} قابل بازیابی باشد؛ در اجرا تصمیم COMMIT ثبت شد و موجودی دو طرف با آن هم‌خوان بود. آزمایش ۵ بار واقعی روی Gateway می‌فرستد تا HPA تعداد replica را از ۲ به ۴ برساند و همزمان موجودی همچنان خوانا بماند. آزمایش ۶ همان بار را هنگام rolling update و rollback نگه می‌دارد تا نشان دهد تعویض Podها موجودی را فاسد نمی‌کند، حتی اگر بخشی از درخواست‌ها موقتاً خطای اتصال بگیرند. آزمایش ۷ یک client_request_id را دو بار می‌فرستد؛ پاسخ دوم با idempotent_replay=true و همان شناسهٔ تراکنش برمی‌گردد و اثر مالی فقط یک‌بار در DB دیده می‌شود.

۱۰. محدودیت‌ها و نتایج

۱۰.۱ آنچه ساخته و اثبات شد

در مجموع، سیستم بانکداری توزیع‌شده با sharding، Gateway و 2PC روی Minikube از روی Manifest قابل بازتولید شد. دادهٔ هر shard پشت PVC ماندگار است، برای shardهای بانک standby با streaming replication و failover مبتنی بر label سرویس writer وجود دارد، و لایهٔ اپ با probes وابسته به DB و Deployment چندنسخه‌ای خودش را ترمیم می‌کند. مقیاس‌پذیری با HPA، آپدیت با RollingUpdate و rollback، و محدودیت شبکهٔ enforce‌شده با Calico — طوری که Gateway به Postgres راه نداشته باشد — همگی پیاده و با شواهد سطح پایگاه‌داده در هفت آزمایش اجباری بررسی شدند.

۱۰.۲ محدودیت‌های پیاده‌سازی

failover دیتابیس در این کار نیمه‌خودکار است: اسکریپت promote و جابه‌جایی label را انجام می‌دهد، ولی جایگزین یک اپراتور کامل مثل Patroni نیست. اگر بعد از failover دوباره کل Manifest اعمال شود، ممکن است StatefulSet مربوط به primary قبلی دوباره بالا بیاید و خطر dual-writer ایجاد کند؛ در آن حالت باید standby از روی writer فعلی rebuild شود و فقط یک Pod برچسب role=primary داشته باشد. روی درایور Docker در ویندوز، NodePort از میزبان پایدار در دسترس نبود و آزمون‌ها با port-forward انجام شدند. همچنین در پنجرهٔ کوتاه rolling update زیر بار بالا، بخشی از درخواست‌ها خطای موقت اتصال می‌گیرند؛ در اجراهای ثبت‌شده فساد موجودی دیده نشد، ولی این خطاهای گذرا بخشی از رفتار واقعی سیستم زیر تعویض Pod هستند. جزئیات استقرار چند-ماشین در بخش بعد آمده است.

هستهٔ سیستم روی Minikube تک‌نود پیاده و آزمایش شد، اما بونوس ۱ می‌خواهد همان بانکداری توزیع‌شده روی یک خوشهٔ واقعی چندماشین اجرا شود: یک control-plane و دو worker، پخش replicaهای اپ بین ورکرها، برای هر shard یک primary ماندگار به‌همراه standby محلی روی همان ورکر و standby دوم روی ورکر دیگر با دیسک مستقل، و در نهایت آزمایش قطع یک ورکر زیر بار بدون فساد موجودی و بدون دو پایگاه writable همزمان. این بخش مسیر ساخت آن خوشه، استقرار اپ، توپولوژی داده، و روش صحت‌سنجی را به‌صورت کامل توضیح می‌دهد. فایل‌های کمکی در 3/k8s/multi-vm/ و 3/k8s/multi-vm/bonus1/ قرار دارند.

۱۱.۴ پایدارسازی Flannel

در ابتدا Podهای کاربری به‌خاطر نبودن /run/flannel/subnet.env در ContainerCreating می‌ماندند و DaemonSet Flannel در CrashLoopBackOff بود. دو علت اصلی پیدا شد: ماژول br_netfilter لود نشده بود، و Flannel به‌جای کارت Host-Only سراغ اینترفیس NAT می‌رفت. روی هر سه نود ماژول و sysctl مربوط فعال شد و روی DaemonSet آرگومان --iface=enp0s8 اضافه گردید. 

# روی هر سه VM

echo br_netfilter >> /etc/modules-load.d/k8s.conf
cat >/etc/sysctl.d/k8s-bridge.conf <<'EOF'
net.bridge.bridge-nf-call-iptables = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward = 1
EOF
sysctl --system

# فقط روی control-plane
kubectl -n kube-flannel patch daemonset kube-flannel-ds --type='json' \
  -p='[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--iface=enp0s8"}]'
kubectl -n kube-flannel delete pods --all
kubectl -n kube-flannel get pods -o wide

پس از این تغییر، هر سه Pod Flannel به حالت Running 1/1 رسیدند و ساخت شبکهٔ Pod برای workloadهای banking ممکن شد.

۱۱.۶ توپولوژی بونوس: standby محلی و راه دور

۱۱.۷ آزمایش قطع ورکر زیر بار

برای نشان دادن تحمل قطع یک worker، اسکریپت interrupt-worker.sh روی control-plane اجرا می‌شود. این اسکریپت ابتدا موجودی یک حساب آزمایشی را از primary می‌خواند، سپس از داخل Pod Gateway یک حلقهٔ deposit پس‌زمینه روی همان حساب راه می‌اندازد، ورکر client-vm را cordon و drain می‌کند، وضعیت نودها و Endpoints نویسنده را ثبت می‌کند، و بعد از uncordon منتظر بازگشت زمان‌بندی می‌ماند. معیار قبول این است که در طول و بعد از قطع، برای هر shard بیش از یک Pod با role=primary دیده نشود، و موجودی حساب آزمایشی نامعتبر یا عقب‌گرد بی‌دلیل نداشته باشد؛ یعنی commitهای موفق از دست نروند و split-brain writer رخ ندهد.
