۱. معماری و نگاشت به منابع Kubernetes

نقطهٔ شروع این پروژه همان پلتفرم Assignment 2 است. هدف بخش اول، تثبیت معماری منطقی و تعیین نگاشت دقیق هر جزء به منبع مناسب Kubernetes است تا استقرار بعدی روی یک طرح واحد انجام شود و routing با تعویض Podها نشکند.

۱.۱ اجزای حفظ‌شده از Assignment 2

قواعد دامنه و مرزهای صحت از Assignment 2 بدون تغییر منتقل می‌شوند:

  • شاردینگ حساب‌ها: بازهٔ A برابر ۱–۱۰۰۰ و بازهٔ B برابر ۱۰۰۱–۲۰۰۰
  • چند replica برنامه‌ای روی هر shard، با یک پایگاه‌دادهٔ مشترک همان shard
  • Gateway آگاه از shard و انتخاب replica سالم برای سرویس‌دهی
  • Coordinator با پروتکل 2PC و ثبت ماندگار تصمیم تراکنش
  • قیود صحت: بدون موجودی تکراری، بدون transfer ناقص دائمی، و بدون اعلام موفقیت برای نتیجهٔ نامعلوم

تفاوت اصلی در لایهٔ اجراست. به‌جای کانتینرهای ثابت Compose، workloadها به‌صورت Pod روی خوشه اجرا می‌شوند و باید در برابر حذف Pod، تغییر مقیاس، rolling update و شکست پایگاه‌داده همچنان در دسترس و صحیح بمانند.

۱.۲ معماری منطقی

معماری منطقی سیستم با Assignment 2 یکسان است. کلاینت فقط با Gateway صحبت می‌کند؛ Gateway درخواست‌های محلی را به shard مربوط و درخواست‌های cross-shard را به Coordinator می‌فرستد. هر لایهٔ اپ به پایگاه‌دادهٔ خودش وابسته است. روی Kubernetes، هویت پایدار برای ارتباط داخلی از نام Service گرفته می‌شود، نه از IP موقتی Pod.

۱.۳ نگاشت اجزا به منابع Kubernetes

انتخاب نوع منبع بر اساس نقش هر جزء در سیستم انجام شده است. سرویس‌های بدون state محلی (Gateway، bank، coordinator، console) با Deployment مدیریت می‌شوند تا بتوان آن‌ها را scale کرد و پس از حذف Pod دوباره ساخت. پایگاه‌های داده که به هویت پایدار و دیسک نیاز دارند با StatefulSet و PersistentVolumeClaim مستقر می‌شوند. کشف و مسیریابی داخلی از طریق Service انجام می‌گیرد و دسترسی خارجی در فاز اول با NodePort فراهم می‌شود.

جزء در Compose منبع Kubernetes توجیه
gateway Deployment + Service (ClusterIP) + NodePort نقطهٔ ورود کلاینت؛ بدون state محلی؛ باید پس از تعویض Pod همچنان از بیرون در دسترس باشد
bank-a* / bank-b* Deployment per shard + Service per shard چند replica برنامه‌ای روی هر shard؛ توزیع ترافیک روی endpointهای Ready
coordinator Deployment + Service منطق 2PC بدون state محلی در فرآیند؛ ماندگاری تصمیم‌ها در db-coord
console Deployment + Service (دسترسی خارجی اختیاری) رابط آزمایشگاهی برای مشاهده و اجرای سناریوها
db-a / db-b / db-coord StatefulSet + PVC (و در ادامه primary/standby) داده باید پس از حذف یا جابه‌جایی Pod باقی بماند؛ هویت پایدار برای replication لازم است
config/shard_map.json ConfigMap پیکربندی غیرحساس و قابل نسخه‌گذاری جدا از ایمیج
رمز عبور و credentialهای پایگاه‌داده Secret جداسازی اسرار از ایمیج و Manifestهای عمومی

۱.۴ استقرار فیزیکی هدف روی Minikube

استقرار هدف در یک namespace جدا (مثلاً banking) روی Minikube تعریف می‌شود. شکل ۲ رابطهٔ Deploymentها، Serviceها و StatefulSetها را نشان می‌دهد. Gateway به نام Service بانک‌ها و Coordinator وصل می‌شود؛ بانک‌ها به Service مربوط به پایگاه‌دادهٔ همان shard؛ و ماندگاری داده روی PVC پشت StatefulSetها قرار می‌گیرد. replication واقعی primary/standby در بخش مربوط به failover اضافه می‌شود.

۱.۵ جریان درخواست و پایداری routing

در Kubernetes عمر Pod محدود است و با هر recreate، آدرس IP عوض می‌شود. اتصال مستقیم Gateway به IP یک Pod پس از restart همان Pod مسیر را می‌شکند. طراحی این سیستم Gateway را فقط به نام Service متصل می‌کند؛ برای مثال http://bank-a:8000. کنترل‌پلن Kubernetes فهرست endpointهای Ready را به‌روز نگه می‌دارد و ترافیک فقط به Podهای سالم هدایت می‌شود. همین سازوکار پایهٔ تحمل خطای سطح اپ و آماده‌سازی برای readiness probe است.

۱.۶ تصمیم‌های طراحی تثبیت‌شده

  • خوشهٔ هدف: Minikube روی میزبان توسعه
  • جداسازی منطقی با namespace اختصاصی (مثلاً banking)
  • دسترسی خارجی فاز اول از طریق NodePort
  • workloadهای اپلیکیشن با Deployment؛ پایگاه‌های داده با StatefulSet و PVC
  • ارتباط داخلی صرفاً از طریق DNS سرویس Kubernetes
  • بازیابی سطح اپلیکیشن با کنترلرهای بومی Kubernetes؛ بدون اتکا به Healer سفارشی Assignment 2 در محدودهٔ اصلی

۲. استقرار هسته روی Minikube

۲.۱ خاموش‌کردن استک Compose (Assignment 2)

کانتینرهای Compose و Podهای Kubernetes هم‌زمان لازم نیستند. با پایین آوردن پروژهٔ Compose، پورت‌های میزبان آزاد می‌شوند و مشخص است که ترافیک از مسیر Kubernetes می‌آید. ایمیج‌ها روی دیسک می‌مانند؛ فقط کانتینرهای در حال اجرا متوقف می‌شوند.

۲.۲ استفاده از ایمیج‌های محلی (بدون دانلود مجدد)

Manifestها به همان ایمیج‌هایی اشاره می‌کنند که قبلاً با docker compose build ساخته شده‌اند. مقدار imagePullPolicy: Never مانع pull از رجیستری می‌شود؛ بنابراین از GitHub/GHCR دوباره دانلود نمی‌شود.

Workload در Kubernetes ایمیج محلی Docker یادداشت
Deployment/bank-a 2-bank-a1:latest همان ایمیج bank_server؛ دو Pod از همین ایمیج
Deployment/bank-b 2-bank-b1:latest همان ایمیج bank_server برای shard B
Deployment/gateway 2-gateway:latest بدون تغییر کد؛ فقط env و مسیر config
Deployment/coordinator 2-coordinator:latest shard map از ConfigMap mount می‌شود

Console مربوط به Assignment 2 در محدودهٔ فعلی استقرار نمی‌شود: به Docker socket و شناسه‌های ثابت A1/A2/B1/B2 وابسته است و هدف این تمرین Kubernetes است، نه بازتولید همان UI. آزمون‌ها از طریق Gateway و kubectl انجام می‌شوند.

نمونهٔ ارجاع ایمیج در Manifest (bank-a):

image: 2-bank-a1:latest
imagePullPolicy: Never

۲.۵ نگاشت DNS و shard map

در Kubernetes، Gateway دیگر به نام‌های ثابت Compose مثل bank-a1 وابسته نیست. shard map به Serviceهای پایدار اشاره می‌کند: http://bank-a:8000 و http://bank-b:8000. خود Service ترافیک را بین Podهای Ready همان Deployment پخش می‌کند. Coordinator نیز از http://coordinator:8090 در دسترس Gateway است و پایگاه‌ها با نام‌های db-a، db-b و db-coord resolve می‌شوند. این تغییر عمدی است: با تعویض Pod، مسیر از روی نام Service درست می‌ماند.

محتوای shard map روی خوشه:

{
  "epoch": 1,
  "shards": {
    "A": { "start": 1, "end": 1000, "replicas": ["http://bank-a:8000"] },
    "B": { "start": 1001, "end": 2000, "replicas": ["http://bank-b:8000"] }
  }
}

۲.۷ بررسی ساختار استقرار

پس از apply، صحت استقرار در دو لایه چک می‌شود: منابع Kubernetes (Pod / Service / StatefulSet / PVC) و رفتار Gateway از بیرون خوشه. روی Windows با درایور Dockerِ Minikube، برای تماس با Gateway از kubectl port-forward استفاده می‌شود.

۱) وضعیت کلی namespace:

انتظار: هر دو replica مربوط به bank-a و bank-b در حالت Running و Ready 1/1؛ سه StatefulSet دیتابیس Ready؛ PVCها Bound؛ و Serviceهای gateway، bank-a، bank-b، coordinator، db-* موجود باشند.

۲) جزئیات هر لایه:

kubectl -n banking get cm,secret

۳) لاگ مختصر در صورت نیاز:

۲.۸ آزمون کارکردی از طریق Gateway

تونل محلی (در یک ترمینال باز بماند):

kubectl -n banking port-forward svc/gateway 8080:8080

در ترمینال دیگر (PowerShell — از curl.exe استفاده شود، نه aliasِ curl):

curl.exe http://127.0.0.1:8080/health
curl.exe http://127.0.0.1:8080/shard-map

پاسخ مورد انتظار: /health وضعیت سالم Gateway را برمی‌گرداند و /shard-map برای هر دو bank-a و bank-b مقدار healthy: true نشان می‌دهد. این یعنی DNS سرویس، readiness، و انتخاب upstream توسط Gateway درست است.

نمونهٔ تراکنش محلی روی shard A (حساب‌های ۱–۱۰۰۰):

curl.exe -X POST http://127.0.0.1:8080/transaction -H "Content-Type: application/json" -d "{\"action\":\"balance\",\"account\":\"A0500\"}"

نمونه روی shard B (حساب‌های ۱۰۰۱–۲۰۰۰):

curl.exe -X POST http://127.0.0.1:8080/transaction -H "Content-Type: application/json" -d "{\"action\":\"balance\",\"account\":\"A1500\"}"

معادل خالص PowerShell (بدون curl.exe):

Invoke-RestMethod http://127.0.0.1:8080/health
Invoke-RestMethod http://127.0.0.1:8080/shard-map
Invoke-RestMethod http://127.0.0.1:8080/transaction -Method POST -ContentType "application/json" -Body '{"action":"balance","account":"A0500"}'
Invoke-RestMethod http://127.0.0.1:8080/transaction -Method POST -ContentType "application/json" -Body '{"action":"balance","account":"A1500"}'

در پاسخ موفق، فیلد مربوط به replica نام Pod بانک را نشان می‌دهد (مثلاً پیشوند bank-a- یا bank-b-). این معیار صحت routing است؛ نه دیاگرام UI قبلی Compose.

۳. Persistence با PersistentVolumeClaim

پایگاه‌های داده با StatefulSet و volumeClaimTemplates مستقر شده‌اند. برای هر نمونه یک PVC جدا ساخته می‌شود (مثلاً data-db-a-0) و به مسیر دادهٔ Postgres mount می‌شود. هدف این بخش اثبات این است که حذف Pod دیتابیس داده را پاک نمی‌کند؛ برخلاف storage موقت مثل emptyDir که با عمر Pod از بین می‌رود.

۳.۱ وضعیت PVC و StatefulSet

مشاهدهٔ claimها و اتصال به volume:

kubectl -n banking get sts,pvc -o wide
kubectl -n banking describe pvc data-db-a-0

در استقرار فعلی هر سه claim در وضعیت Bound هستند و به StorageClass پیش‌فرض Minikube (standard) وصل‌اند. نام PVC از الگوی <claimName>-<podName> می‌آید؛ بنابراین برای db-a-0 نام data-db-a-0 ثابت می‌ماند حتی اگر خود Pod دوباره ساخته شود.

۳.۲ آزمایش ماندگاری داده

سناریو: موجودی حساب A0500 را تغییر می‌دهیم، Pod db-a-0 را حذف می‌کنیم، و پس از Ready شدن مجدد همان موجودی را می‌خوانیم. اگر PVC درست کار کند، مقدار بعد از recreate باید همان مقدار بعد از deposit باشد.

تونل Gateway (ترمینال جدا):

kubectl -n banking port-forward svc/gateway 8080:8080

۱) موجودی اولیه و deposit:

Invoke-RestMethod http://127.0.0.1:8080/transaction -Method POST -ContentType "application/json" -Body '{"action":"balance","account":"A0500"}'
Invoke-RestMethod http://127.0.0.1:8080/transaction -Method POST -ContentType "application/json" -Body '{"action":"deposit","account":"A0500","amount":50}'
Invoke-RestMethod http://127.0.0.1:8080/transaction -Method POST -ContentType "application/json" -Body '{"action":"balance","account":"A0500"}'

۲) حذف Pod دیتابیس shard A و انتظار برای جایگزینی:

kubectl -n banking delete pod db-a-0
kubectl -n banking rollout status statefulset/db-a --timeout=120s
kubectl -n banking get pod db-a-0 -o wide
kubectl -n banking get pvc data-db-a-0

۳) خواندن مجدد موجودی:

Invoke-RestMethod http://127.0.0.1:8080/transaction -Method POST -ContentType "application/json" -Body '{"action":"balance","account":"A0500"}'

۳.۳ نتایج مشاهده‌شده

گام نتیجه
balance قبل از deposit 1000.0
پس از deposit به اندازهٔ ۵۰ 1050.0
حذف db-a-0 StatefulSet Pod جدید ساخت؛ IP عوض شد (مثلاً به 10.244.0.16)
وضعیت PVC همان data-db-a-0 همچنان Bound به همان Volume
balance بعد از recreate 1050.0 — داده باقی ماند

جمع‌بندی: Pod موقتی است و IP عوض می‌شود، اما دیسک پشت PVC پایدار است. به همین دلیل برای پایگاه‌داده StatefulSet+PVC انتخاب شده و برای اپ‌های بدون state محلی، Deployment کافی است. اگر به‌جای PVC از emptyDir استفاده می‌شد، با حذف Pod موجودی به حالت اولیه برمی‌گشت.
