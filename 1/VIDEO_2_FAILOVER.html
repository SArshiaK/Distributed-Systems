🎬 ویدیو ۲ — بونوس اول: تاب‌آوری و انتقال خودکار ترافیک (Failover - +۱۰٪)

این ویدیو برای بخش بونوس ۱۰٪ است و سناریوی زیر را به تصویر می‌کشد: ارسال درخواست‌های پیوسته کلاینت، کشتن ناگهانی سرور اصلی A در میانه ترافیک، انتقال خودکار و بدون وقفه به سرور پشتیبان B، ارتقای اتوماتیک دیتابیس B با pg_promote و ثبت تراکنش‌های بعدی بدون دخالت دست.
مدت زمان تقریبی: حدود ۲ دقیقه

آماده‌سازی قبل از ضبط

  • Server A (Primary): در ترمینال با python server.py در حال اجراست (.101)
  • Server B (Replica): در ترمینال با python server.py در حال اجراست (.104)
  • Client VM: ترمینال آماده است (.102)

پیش‌نیاز بسیار مهم:

مطمئن شوید دیتابیس سرور B هنوز در حالت Standby Replica است. برای اطمینان، روی سرور A دستور زیر را بزنید و باید وضعیت streaming بدهد:

sudo -u postgres psql -c "SELECT client_addr, state FROM pg_stat_replication;"

بخش ۱ — معرفی سناریوی Failover (۰:۰۰ — ۰:۳۰)

متن پیشنهادی برای روایت صوتی:

"در این ویدیو بخش پیشرفته اول یعنی کلاستر با تحمل‌پذیری در برابر خرابی (Fault Tolerance) به همراه مکانیزم Failover خودکار با ارزش ۱۰ درصد نمره امتیازی را نمایش می‌دهیم. در این معماری، سرور A در نقش Primary و سرور B در نقش Standby Replica با استفاده از PostgreSQL Streaming Replication همگام هستند. کلاینت دارای لیستی از هر دو سرور است. اکنون ترافیک پیوسته ایجاد می‌کنیم و در میانه کار، سرور A را به طور ناگهانی متوقف می‌سازیم تا رفتار انتقال بدون وقفه سامانه را مشاهده کنیم."

بخش ۲ — شروع ترافیک و کشتن ناگهانی Server A (۰:۳۰ — ۱:۱۵)

۱. اجرای دستور در ترمینال Client VM:

python3 client.py failover-demo A1001

۲. اقدام حین اجرا (در درخواست ۵ یا ۶):

سریعاً به ترمینال Server A رفته و دکمه‌های Ctrl+C را بزنید تا پروسه سرور کشته شود.

۳. خروجی که در کلاینت نمایان می‌شود:

Request  1: success  balance=1000.0  server=http://192.168.56.101:8000
...
Request  5: success  balance=1000.0  server=http://192.168.56.101:8000
Request  6: success  balance=1000.0  server=http://192.168.56.104:8000  <-- سوئیچ به سرور B!
Request  7: success  balance=1000.0  server=http://192.168.56.104:8000
...

روایت:

"همان‌طور که مشاهده می‌کنید، درخواست‌ها ابتدا توسط سرور A پاسخ داده می‌شوند. در میانه درخواست‌ها، سرور A را با Ctrl+C می‌کشیم. کلاینت بلافاصله قطعی سرور A را تشخیص داده و بدون نمایش هیچ‌گونه خطایی، درخواست بعدی را به سرور B ارسال می‌کند. ترافیک بدون حتی یک میلی‌ثانیه وقفه یا کرش به مسیر خود ادامه می‌دهد."

بخش ۳ — ثبت تراکنش‌های جدید روی Server B ارتقایافته (۱:۱۵ — ۱:۵۰)

حالا باید نشان دهیم سرور B فقط یک آینه خواندنی نیست، بلکه به طور خودکار به Master تبدیل شده و تراکنش‌های نوشتن را می‌پذیرد:

دستورات در ترمینال Client VM:

python3 client.py deposit A1001 50
python3 client.py withdraw A1001 20
python3 client.py balance A1001

روایت:

"اکنون در حالی که سرور A کاملاً خاموش است، تراکنش‌های واریز ۵۰ تومان و برداشت ۲۰ تومان را ارسال می‌کنیم. سرور B در اولین درخواست نوشتن، متوجه وضعیت ریکاوری دیتابیس شده و با فراخوانی تابع pg_promote()، پایگاه داده خود را به صورت خودکار به Master ارتقا می‌دهد. تراکنش‌های واریز و برداشت با موفقیت انجام شده و موجودی نهایی دقیقاً محاسبه می‌شود. هیچ تراکنشی مفقود نشده و هیچ عملیاتی دو بار اعمال نگردیده است."

بخش ۴ — بازگشت Server A و تبدیل شدن به رپلیکای جدید (۱:۵۰ — ۲:۴۰)

پس از ارتقای B، دیتابیس A هنوز یک primary قدیمی است. چون Streaming Replication ذاتاً یک‌طرفه است، بین دو primary هیچ WAL جابه‌جا نمی‌شود و replication تا بازسازی A متوقف می‌ماند. برنامه این وضعیت را خودکار تشخیص می‌دهد (مقایسهٔ timeline) و روی A درخواست‌ها را با 503 stale primary رد می‌کند تا کلاینت به B برود.

۱. پیش‌نیاز یک‌باره روی Server B (اجازهٔ replication به A):

sudo bash -c 'cat >> /etc/postgresql/*/main/pg_hba.conf << EOF
host    replication     replicator      192.168.56.101/32       md5
host    minibank        bankuser        192.168.56.0/24         md5
EOF'
sudo systemctl reload postgresql

۲. روی Server A — برنامه را ببندید و سپس:

sudo bash rejoin_as_replica.sh

اسکریپت ابتدا مطمئن می‌شود B واقعاً primary است، سپس دیتابیس قدیمی را کنار می‌گذارد، از B کلون می‌گیرد و A را به‌صورت standby بالا می‌آورد.

۳. بررسی:

# روی Server A
sudo -u postgres psql -tAc "SELECT pg_is_in_recovery()"               # t
sudo -u postgres psql -c "SELECT status FROM pg_stat_wal_receiver;"  # streaming

# روی Server B
sudo -u postgres psql -c "SELECT client_addr, state FROM pg_stat_replication;"
# 192.168.56.101 | streaming

۴. اجرای مجدد برنامه روی Server A:

source venv/bin/activate && python3 server.py

روایت:

"وقتی سرور A برمی‌گردد، دیگر نمی‌تواند primary بماند، چون تغییرات جدید روی B ثبت شده‌اند. با مقایسهٔ timeline، سامانه تشخیص می‌دهد A عقب‌تر است و آن را فقط‌خواندنی می‌کند. سپس با اسکریپت rejoin، دیتابیس A از B بازسازی می‌شود و به‌عنوان رپلیکا به کلاستر برمی‌گردد. از این لحظه تغییرات B به A منتقل می‌شوند و هر دو دیتابیس همگام‌اند."
