سناریوی ضبط ویدیو — نمایش دمو سرور تراکنش بانکی توزیع‌پذیر

این سناریو برای ضبط ویدیوی حداکثر ۵ دقیقه‌ای طراحی شده که تمام نیازمندی‌های بخش ۴ سند تمرین (نمایش عملیات عادی، خطاها، دیتاهای همزمان، لاگ‌ها و بخش‌های بونوس Failover و Split-Brain) را به طور کامل پوشش می‌دهد.

⚠️ نکات مهم قبل از ضبط:
  • کلید شروع ضبط ویدیو را آماده کنید؛ ترجیحاً از OBS Studio یا Xbox Game Bar ویندوز استفاده کنید.
  • خروجی صداiors به صورت «توضیح دادن با صدای خود» حیاتی است — به هیچ عنوان متن را بخوانید و لهجه طبیعی بگیرید.
  • قبل از زدن دکمهٔ رضایت، مطمئن شوید تمام ماشین‌ها روشن هستند و witness.py در ترمینال هاست در حال اجرا است.
  • پنجره‌ها و ترمینال‌ها را دقیقاً به همان ترتیبی چیدمان کنید که در سناریو آمده تا تماشاچی گیج نشود.

مرحله 5: Atomicity + Durability (۲:۳۰ — ۳:۱۰)

⏱ ۴۰ ثانیه

اجرای دستورات در ترمینال Client VM:

python3 client.py withdraw A1001 999999
python3 client.py balance A1001

(انتظار می‌رود موجودی تغییر نکند و خطای "insufficient funds" محقق شود.)

🎙 متن پیشنهادی Atomicity:
"سعی می‌کنیم موجودی غیرممکن برداشت کنیم. تراکنش با شکست مواجه می‌شود و روی موجودی هیچ تأثیری نمی‌گذارد — این اثبات Atomicity است.
🎙 شرح Durability:
حالا مانگاری و مطمئن شویم که سرور کرش شود هیچ دیتایی از دست نمی‌رود. روی ترمینال Server A دکمه Ctrl+C می‌زنیم تا سرور کشته شود و بلافاصله دوباره python server.py را اجرا می‌کنیم. مشاهده می‌کنید که استعلام موجودی برابر همان عدد قبلی است. چون تراکنش Commit شده روی دیسک WAL ثبت گردیده، هیچ چیز از دست نرفته. این اثبات Durability است.

اجرای دستورات در ترمینال Server A (پس از restart):

sudo systemctl restart postgresql
python3 server.py

مرحله 6: نمایش Failover خودکار (+۱۰٪ بونوس) (۳:۱۰ — ۴:۰۰)

⏱ ۵۰ ثانیه

مراحل اجرا:

  • مرحله اول و درخواست‌های عادی در کلاینت انجام شوند (قبل از این مرحله سرور A مجدداً روشن باشد).
  • اجرا عليه‌ی اجرای دستور python3 client.py failover-demo A1001
  • در حین اجرا (Request 5 یا 6) روی کلاینت اجرای سرور A را با Ctrl+C بکشید.
  • برای تأیید آنکه واقعاً سوئچ به سرور B انجام شده، درخواست Deposite کن له:
python3 client.py deposit A1001 25
python3 client.py balance A1001
🎙 متن پیشنهادی:
"این بخش بونوس ۱۰٪ است — قابلیت تحمل‌پذیری در برابر خرابی. کلاینت به صورت حلقه‌ای هر ثانیه به سرور A درخواست می‌فرستد. در وسط اجرا، سرور A را به طور دستی و ناگهانی می‌کشیم. بلافاصله کلاینت در درخواست بعدی خطای اتصال به A را دریافت نکرده، بلکه به‌صورت خودکار به سرور B وصل می‌شود و تراکنش‌ها همچنان سالم ادامه می‌یابند. سرور B به طور خودکار دیتابیس خود را با pg_promote() به Master ارتقا داده و واریز ۲۵ تومانی روی آن موفق اجرا می‌شود. هیچ درخواستی از دست نرفته و هیچ تراکنشی دو بار اعمال نشده است."

مرحله 7: نمایش قطع شبکه و جلوگیری از Split-Brain (+۱۵٪ بونوس) (۴:۰۰ — ۵:۰۰)

⏱ ۶۰ ثانیه

مراحل اجرا:

  1. مطمئن شوید Server A و Server B هر دو بالا هستند (اگر قبلاً سرور A کشته شده، دوباره راه‌اندازی کنید).
  2. مطمئن شوید Witness در حال اجرا است.
  3. در ترمینال Client، وضعیت اولیه را لازم است گزارش کنید:
curl http://192.168.56.101:8000/quorum-status
curl http://192.168.56.104:8000/quorum-status

هر دو نشان می‌دهند {"has_quorum": true}

به‌صورت زنده اجرا در Server B:

# قطع ارتباط شبکه‌ای بین سرور B و سرور اصلی A و همچنین Witness
sudo iptables -A INPUT -s 192.168.56.101 -j DROP
sudo iptables -A OUTPUT -d 192.168.56.101 -j DROP
sudo iptables -A INPUT -s 192.168.56.103 -j DROP
sudo iptables -A OUTPUT -d 192.168.56.103 -j DROP

در حین قطع شبکه، در Client:

curl http://192.168.56.104:8000/quorum-status

نتیجه باید باشد:

{"has_quorum": false, "mode": "read-only", ...}

اجرای درخواست‌ها:

# تست نوشتن (مورد انتظار: ردیفی با خطای 503 no quorum)
curl -X POST http://192.168.56.104:8000/transaction \\
  -H "Content-Type: application/json" \\
  -d '{"action":"deposit","account":"A1001","amount":50}'

# تست استعلام (مورد انتظار: طبق معمول و موفق)
curl -X POST http://192.168.56.104:8000/transaction \\
  -H "Content-Type: application/json" \\
  -d '{"action":"balance","account":"A1001"}'
🎙 متن پیشنهادی:
"این مرحله، بونوس ۱۵٪ است — جلوگیری از سناریوی خطرناک Split-Brain. شبکه بین سرور A و B به همراه ارتباط با Gaudy را قطع می‌کنیم. بلافاصله سرور B تشخیص می‌دهد که تنها مانده و کمتر از رأی اکثریت (۱ از ۳) را دراختیار دارد؛ پس فوراً به حالت Read-Only می‌رود (خطای has_quorum false). اگر بخواهیم روی آن واریز کنیم، با خطای استاندارد HTTP 503 'no quorum: server in read-only mode' رد می‌شود، ولی استعلام موجودی به طور عادی پاس کار می‌دهد. در مقابل، سرور A (با حد و رأی اکثریت ۲ از ۳) همچنان تراکنش‌های واریز را می‌پذیرد. این تضمین می‌کند که هیچ‌گاه نتوان دو نسخه متناقض از دیتای یک حساب ساخته شود."

بازیابی و برررسی نهایی (Recovery + Consistency Verification):

# بازگرداندن شبکه در Server B
sudo iptables -F

# روشن مجدد witness روی هاست (Ctrl+C سپس اجرا دوباره)
python witness.py

تست اطمینان در Client:

curl http://192.168.56.101:8000/quorum-status
curl http://192.168.56.104:8000/quorum-status

# در انتها، موجودی را از هر دو سرور استعلام بگیرید — باید یکسان باشند
curl -X POST http://192.168.56.101:8000/transaction \\
  -H "Content-Type: application/json" \\
  -d '{"action":"balance","account":"A1001"}'

curl -X POST http://192.168.56.104:8000/transaction \\
  -H "Content-Type: application/json" \\
  -d '{"action":"balance","account":"A1001"}'
🎙 متن پیشنهادی پس از بازیابی:
"با برگشت شبکه و راه‌اندازی مجدد گره داور، هر دو سرور گزارش می‌دهند که مجدداً has_quorum: true دارند و همه چیز سالم است. استعلام موجودی از هر دو سرور نشان می‌دهد که پس از بازگشت شبکه، تراکنش‌هایPrime Store شده از طریق Streaming Replication به سرور B منتقل گردیده و هر دو سرور دقت یکسان از داده‌های خود پیرامون حساب show می‌دهند. هیچ تراکنشی از دست نرفته و هیچ تراکنشی دو بار اعمال نشده است."

📌 یادآوری نهایی — ترتیب مهم مراحل:
  • سناریوی مرحله ۷ (Network Partition) حتماً قبل از مرحله ۶ (Failover) ضبط شود، چون Failover دیتابیس B را به Master ارتقا می‌دهد و دیگر رپلیکا نخواهد بود.
  • اگر مرحله ۶ قبل از مرحله ۷ ضبط شد، حتماً Server B را با دستور pg_basebackup دوباره بازسازی (Re-sync) کنید.
  • قبل از اتمام ویدیو حتماً فایل لاگ (bank_server.log) را نمایش دهید.
  • تا زمانی که مرحله ۷ کامل نشده، ویدیو را نبندید.
