🎬 ویدیو ۳ — بونوس دوم: انقطاع شبکه و جلوگیری از دوپارگی مغز (Split-Brain - +۱۵٪)

این ویدیو برای نشان دادن سناریوی پیچیده بخش ۶ سند تمرین است: انقطاع واقعی شبکه بین ماشین‌های سرور با استفاده از iptables، رفتار سامانه حین انقطاع (رفتن سرور ایزوله به حالت Read-Only و رد تراکنش‌های نوشتن با خطای ۵۰۳ به دلیل فقدان حدنصاب Quorum، مجاز بودن استعلام موجودی)، پذیرش تراکنش‌ها توسط سرور واجد اکثریت، و در نهایت بازگرداندن اتصال شبکه و اثبات همگام‌سازی سالم داده‌ها بدون مغایرت (Healing).
مدت زمان تقریبی: حدود ۳ دقیقه

آماده‌سازی قبل از ضبط

  • Witness: در هاست با python witness.py در حال اجراست (.103:9000)
  • Server A: در ترمینال با python server.py در حال اجراست (.101:8000)
  • Server B: در ترمینال با python server.py در حال اجراست (.104:8000)
  • Client VM: ترمینال آماده است (.102)

نکته کلیدی: در حالت عادی، سرور B با سرور A و Witness در ارتباط است (۳ رأی). برای شبیه‌سازی ایزوله شدن کامل سرور B، اتصال آن را هم به سرور A و هم به Witness مسدود می‌کنیم تا رأی آن ۱ از ۳ شود و فاقد حدنصاب (No Quorum) گردد.

هشدار ترتیب ضبط

این سناریو فرض می‌کند Server A همچنان primary و Server B استندبای است. اگر ویدیوی Failover (+۱۰٪) را قبلاً ضبط کرده‌اید، B اکنون primary شده و A رپلیکای آن است. در این صورت یا این ویدیو را قبل از ویدیوی Failover ضبط کنید، یا دیتابیس B را با pg_basebackup از A دوباره به استندبای تبدیل کنید (بخش ۳.۳ گزارش).

منطق دقیق Witness و Quorum (برای روایت)

  1. هر سرور برای خودش یک رأی ثابت دارد.
  2. اگر به سرور همتا وصل شود (GET /health) یک رأی می‌گیرد.
  3. اگر Witness جواب دهد (GET /ping) یک رأی می‌گیرد.
  4. حدنصاب = ۲ رأی از ۳. کمتر از آن یعنی فقط‌خواندنی و رد نوشتن با خطای ۵۰۳.

در این دمو، Server B را از هر دو نود دیگر قطع می‌کنیم، پس فقط ۱ رأی دارد و read-only می‌شود. Server A همچنان Witness را می‌بیند: ۱ (خود) + ۱ (Witness) = ۲ → مجاز به نوشتن. Witness هیچ داده‌ای نگه نمی‌دارد؛ فقط داور است.

نکته عمیق (اختیاری برای نمره بیشتر)

شمارش سادهٔ رأی یک نقطهٔ کور دارد: اگر فقط لینک A↔B قطع شود ولی هر دو به Witness دسترسی داشته باشند، هر دو ۲ رأی می‌گیرند و هر دو خود را primary می‌دانند. برای بستن این سوراخ، حالت Lease اضافه شده است: Witness یک «اجاره‌نامهٔ انحصاری» به فقط یک سرور می‌دهد و سرور تنها تا زمانی می‌نویسد که دارندهٔ اجاره باشد. این حالت اختیاری است و با ENABLE_LEASE=true فعال می‌شود (بخش ۵ در انتها).

بخش ۱ — معرفی سناریوی Split-Brain و مدل حدنصاب (۰:۰۰ — ۰:۳۵)

متن پیشنهادی برای روایت صوتی:

"در این بخش، سناریوی Extreme Bonus با ارزش ۱۵٪ نمره را بررسی می‌کنیم: انقطاع شبکه (Network Partition) و جلوگیری از دوپارگی مغز (Split-Brain). اگر ارتباط بین دو سرور قطع شود اما هر دو روشن بمانند، ممکن است هر دو سرور خود را Master دانسته و شروع به ثبت تراکنش‌های متناقض کنند. سامانه ما با مدل حدنصاب اکثریت ۳ عضوی (Quorum = ۲ از ۳ شامل سرور A، سرور B و گره داور Witness) از این فاجعه جلوگیری می‌کند. ابتدا وضعیت اولیه هر دو سرور را بررسی می‌کنیم."

اجرا در ترمینال Client VM:

curl http://192.168.56.101:8000/quorum-status
curl http://192.168.56.104:8000/quorum-status

هر دو سرور مقدار {"has_quorum": true, "mode": "primary"} برمی‌گردانند.

بخش ۲ — ایجاد انقطاع واقعی شبکه با iptables (۰:۳۵ — ۱:۱۵)

به ترمینال Server B رفته و دستورات زیر را برای قطع کامل ارتباط با سرور A و Witness اجرا کنید:

دستورات در ترمینال Server B:

sudo iptables -A INPUT -s 192.168.56.101 -j DROP
sudo iptables -A OUTPUT -d 192.168.56.101 -j DROP
sudo iptables -A INPUT -s 192.168.56.103 -j DROP
sudo iptables -A OUTPUT -d 192.168.56.103 -j DROP

روایت:

"با استفاده از فایروال iptables در سطح سیستم‌عامل سرور B، ارتباط آن را با سرور A و گره Witness قطع کردیم. این یک انقطاع فیزیکی واقعی است و نه صرفاً بستن پروسه پایتون. اکنون سرور B کاملاً در شبکه تنها مانده و فقط ۱ رأی از ۳ رأی را در اختیار دارد."

بخش ۳ — اثبات حالت فقط‌خواندنی (Read-Only) روی Server B ایزوله (۱:۱۵ — ۲:۰۰)

۱. بررسی وضعیت حدنصاب از کلاینت:

curl http://192.168.56.104:8000/quorum-status

خروجی: {"has_quorum": false, "mode": "read-only"}

۲. تلاش برای واریز به Server B ایزوله (باید رد شود):

curl -X POST http://192.168.56.104:8000/transaction \
  -H "Content-Type: application/json" \
  -d '{"action":"deposit","account":"A1001","amount":50}'

خروجی: HTTP 503 {"status": "error", "message": "no quorum: server in read-only mode..."}

۳. استعلام موجودی از Server B (باید کار کند):

curl -X POST http://192.168.56.104:8000/transaction \
  -H "Content-Type: application/json" \
  -d '{"action":"balance","account":"A1001"}'

خروجی: HTTP 200 {"status": "success", "balance": ...}

۴. پذیرش تراکنش توسط Server A (چون حدنصاب ۲ از ۳ دارد):

python3 client.py deposit A1001 100

روایت:

"مشاهده می‌کنید که سرور B تشخیص داده حدنصاب ندارد و حالت read-only گرفته است. وقتی سعی می‌کنیم روی سرور B واریز انجام دهیم، بلافاصله با خطای ۵۰۳ 'no quorum' تراکنش را ریجکت می‌کند تا اطلاعات دوشاخه نشود؛ اما استعلام موجودی همچنان کار می‌کند. در مقابل، سرور A چون به گره Witness دسترسی دارد و اکثریت را داراست، تراکنش‌های واریز را به درستی می‌پذیرد. این اثبات قطعی ممانعت از Split-Brain است."

بخش ۴ — بازگرداندن شبکه و همگام‌سازی کامل (Recovery — ۲:۰۰ — ۲:۴۵)

به ترمینال Server B رفته و فایروال را پاک‌سازی کنید:

دستور در ترمینال Server B:

sudo iptables -F

۵ ثانیه صبر کنید تا شبکه متصل و replication همگام شود، سپس در Client VM دستورات زیر را اجرا کنید:

دستورات در ترمینال Client VM:

# بررسی بازگشت حدنصاب
curl http://192.168.56.101:8000/quorum-status
curl http://192.168.56.104:8000/quorum-status

# استعلام موجودی از هر دو سرور — باید کاملاً یکسان باشند
curl -X POST http://192.168.56.101:8000/transaction \
  -H "Content-Type: application/json" \
  -d '{"action":"balance","account":"A1001"}'

curl -X POST http://192.168.56.104:8000/transaction \
  -H "Content-Type: application/json" \
  -d '{"action":"balance","account":"A1001"}'

روایت پایانی:

"با دستور iptables -F اتصال شبکه را بازگرداندیم. بلافاصله هر دو سرور وضعیت has_quorum: true را به دست آوردند. تغییراتی که حین انقطاع روی سرور A ثبت شده بود، از طریق Streaming Replication به سرور B منتقل شد. همان‌طور که می‌بینید، موجودی هر دو سرور دقیقاً یکسان است. سامانه بعد از انقطاع، به طور کامل و بدون کوچک‌ترین تداخل داده‌ای خود را بازیابی کرد. متشکرم."

بخش ۵ (اختیاری) — اثبات با Lease: وقتی هر دو سرور Witness را می‌بینند (۲:۴۵ — ۳:۳۰)

این بخش اختیاری نشان می‌دهد چرا «شمارش رأی» به‌تنهایی کافی نیست و Lease چطور آن را کامل می‌کند.

۱. فعال‌سازی روی هر دو سرور (در فایل .env):

ENABLE_LEASE=true
NODE_ID=server-a          # روی Server B: server-b
LEASE_TTL=6
LEASE_RENEW_INTERVAL=2

هر دو سرور را ری‌استارت کنید. سپس رهبر را ببینید:

curl http://192.168.56.101:8000/quorum-status
curl http://192.168.56.104:8000/quorum-status

انتظار: روی A مقدار "lease": {"is_leader": true, "leader": "server-a"} و روی B "is_leader": false با mode: read-only.

۲. حالا فقط لینک A↔B را قطع کنید (هر دو به Witness وصل می‌مانند):

sudo iptables -A INPUT -s 192.168.56.101 -j DROP
sudo iptables -A OUTPUT -d 192.168.56.101 -j DROP

هر دو سرور has_quorum: true دارند، ولی فقط A اجازهٔ نوشتن دارد:

curl -X POST http://192.168.56.104:8000/transaction \
  -H "Content-Type: application/json" \
  -d '{"action":"deposit","account":"A1001","amount":50}'

خروجی: HTTP 503 {"message": "not primary: server in read-only mode (lease not held)"} — یعنی حتی با داشتن ۲ رأی، B نمی‌تواند بنویسد، چون اجاره‌نامه دست A است.

۳. حالا Server A را ببندید (Ctrl+C):

حداکثر بعد از LEASE_TTL ثانیه، B اجاره را می‌گیرد و primary می‌شود: 

curl http://192.168.56.104:8000/quorum-status

انتظار: "lease": {"is_leader": true, "leader": "server-b"} و mode: primary.

پاک‌سازی:

sudo iptables -F
"این بخش نشان داد که Lease یک انتخاب انحصاری است، نه شمارش محلی رأی: در هر لحظه فقط یک دارندهٔ اجاره وجود دارد. اگر Witness از دسترس خارج شود، سرورها پس از پایان TTL به حالت فقط‌خواندنی می‌روند — یعنی سامانه ترجیح می‌دهد نوشتن را متوقف کند تا داده دوشاخه نشود."
