گزارش فنی پلتفرم بانکداری توزیع‌شده

۱. مقدمه و هدف

هدف سیستم، سرویس بانکداری با مقیاس افقی است: حساب‌ها بین چند پایگاه‌داده (shard) پخش می‌شوند، Gateway مسیر را از روی Shard Map پیدا می‌کند، و انتقال بین‌shard با Coordinator و پروتکل Two-Phase Commit انجام می‌شود. استقرار با Docker Compose است و روی سرویس‌های بانکی restart: "no" گذاشته شده تا بازیابی replica در Bonus II توسط منطق خودمان باشد، نه Swarm/Kubernetes یا restart خودکار Docker.

۲. مرحله ۱ — هستهٔ ساده

در اولین لایه فقط یک مسیر وجود دارد: کلاینت به Gateway می‌رسد، Gateway به یک سرویس بانکی می‌فرستد، و بانک روی Postgres می‌نویسد. هنوز sharding و 2PC نیست؛ فقط قرارداد «یک ورودی برای همهٔ درخواست‌ها» ثابت می‌شود.

۳. مرحله ۲ — Sharding و Shard Map

فضای حساب‌ها با شناسهٔ Axxxx به بازه‌ها شکسته می‌شود و در config/shard_map.json ثبت می‌گردد. Gateway با شمارهٔ حساب، shard مالک را پیدا می‌کند. فیلد epoch نسخهٔ منطقی map است و هنگام مهاجرت زنده افزایش می‌یابد.

  • Shard A: ۱–۱۰۰۰ → db-a
  • Shard B: ۱۰۰۱–۲۰۰۰ → db-b
  • Shard C (بعد از Bonus I): معمولاً ۱۵۰۱–۲۰۰۰ → db-c

۴. مرحله ۳ — Replicaها و Load Balancing

هر shard دست‌کم دو نمونهٔ برنامه دارد که به یک دیتابیس مشترک وصل‌اند (مثلاً bank-a1 و bank-a2 روی db-a). Gateway حدود هر ۲ ثانیه /health را می‌زند و فقط replicaهای سالم را با round-robin انتخاب می‌کند. قطع یک peer، ترافیک را روی سالم نگه می‌دارد—پایهٔ Bonus II.

۵. مرحله ۴ — تراکنش محلی در برابر Cross-Shard

اگر مبدأ و مقصد transfer در یک shard باشند، Gateway مستقیم به یک replica همان shard می‌فرستد. اگر دو shard متفاوت باشند، درخواست به Coordinator می‌رود تا 2PC اجرا شود—Gateway دیگر خودش پول را جابه‌جا نمی‌کند.

۶. مرحله ۵ — پروتکل 2PC و توالی پیام‌ها

Coordinator وضعیت را در db-coord نگه می‌دارد: PREPARING → رأی‌گیری → در صورت موفقیت، ثبت ماندگار COMMIT_DECIDED → ارسال COMMIT → COMPLETED. اگر رأی منفی یا خطا باشد مسیر ABORT طی می‌شود.

# مسیر عمل
1 Client → Gateway درخواست transfer بین‌shard
2 Gateway → Coordinator شروع 2PC با client_request_id
3–4 Coordinator ⇄ Banks PREPARE و جمع‌آوری رأی
5 Coordinator / db-coord ثبت ماندگار COMMIT_DECIDED یا ABORT
6–7 Coordinator → Banks → Client اعمال نهایی و پاسخ

۷. تصمیم ماندگار و بازیابی Coordinator

اگر Coordinator بعد از COMMIT_DECIDED و قبل از ACK همهٔ شرکت‌کننده‌ها کرش کند، هنگام بالا آمدن از وضعیت ماندگار می‌فهمد تصمیم commit بوده و دوباره COMMIT را می‌فرستد تا به COMPLETED برسد—بدون دو بار جابه‌جایی پول. کرش قبل از تصمیم نهایی به مسیر abort/ایمن می‌رود. آزمایش ۶ همین سناریو را نشان می‌دهد.

۸. کنترل همزمانی و صحت

تراکنش‌های محلی با قفل SQL محافظت می‌شوند؛ در 2PC فاز PREPARE منابع را تا تصمیم نهایی نگه می‌دارد. client_request_id باعث idempotency می‌شود تا retry کلاینت موجودی را دو بار تغییر ندهد. «Preserve transaction correctness» یعنی همین ایمنی منطقی است، نه صف خودکار برای replay همهٔ درخواست‌های fail‌شده هنگام قطع کامل یک shard.

۹. Bonus I — مهاجرت زندهٔ Shard

بازهٔ A1501–A2000 از مالک B به C منتقل می‌شود در حالی که ترافیک ادامه دارد و در هیچ لحظه دو نویسندهٔ همزمان برای یک حساب وجود ندارد.

  1. PROVISION_TARGET — بالا آوردن C با نوشتن خاموش
  2. SNAPSHOT — کپی سازگار بازه از B به C
  3. CATCHUP — replay تغییرات از changelog (CDC)
  4. FENCE_SOURCE — فنس کوتاه نوشتن روی بازه در B
  5. FINAL_CATCHUP + WAIT_INFLIGHT_2PC — جمع‌کردن باقی‌مانده و تراکنش‌های باز
  6. ACTIVATE_MAP — epoch جدید، فعال‌سازی C، reload Gateway/Coordinator
  7. VERIFY + CLEANUP — صحت مسیرها و حذف دادهٔ کهنه از B

۱۰. Bonus II — Autonomous Self-Healing

سرویس Healer بدون Swarm/K8s و بدون restart policy داکر، تعداد replica سالم را حفظ می‌کند. حلقه حدود هر ۲ ثانیه به /health هر slot می‌زند؛ دو شکست پیاپی نامزدی جایگزینی می‌سازد. قبل از create، intent در healer_state.json نوشته می‌شود تا کرش کنترلر باعث duplicate نشود. سپس کانتینر جدید با Docker API ساخته می‌شود، سالم می‌شود، در Shard Map ثبت و به Gateway/Coordinator اعلام می‌گردد؛ در پایان کانتینر خراب حذف می‌شود. peer سالم در تمام مدت به ترافیک پاسخ می‌دهد.

۱۱. محدودیت‌ها و نتایج

نتایج قابل‌نمایش در دمو

  • مسیریابی shard-aware برای عملیات محلی و cross-shard
  • ادامهٔ سرویس با یک replica هنگام توقف peer
  • بازیابی 2PC پس از کرش Coordinator در COMMIT_DECIDED
  • مهاجرت زنده B→C با fence، catchup و epoch جدید
  • جایگزینی خودکار replica و ثبت در Gateway زیر ترافیک

محدودیت‌ها

  • Replicaهای یک shard دیتابیس مشترک دارند.
  • خرابی هم‌زمان همهٔ replicaهای یک shard باعث fail موقت است تا اولین جایگزین بالا بیاید.
  • مهاجرت برای بازه و سناریوی آزمایشگاهی بهینه‌شده است.
جمع‌بندی: سیستم از یک Gateway ساده به بانک shardشده با 2PC بادوام، مهاجرت آنلاین و کنترلر خودترمیم‌گر می‌رسد؛ هر لایه روی همان قرارداد Shard Map سوار می‌شود.
